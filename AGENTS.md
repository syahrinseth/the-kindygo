- You can and should pass multiple queries at once. The most relevant results will be returned first.

1. Simple Word Searches with auto-stemming - query=authentication - finds 'authenticate' and 'auth'
2. Multiple Words (AND Logic) - query=rate limit - finds knowledge containing both "rate" AND "limit"
3. Quoted Phrases (Exact Position) - query="infinite scroll" - Words must be adjacent and in that order
4. Mixed Queries - query=middleware "rate limit" - "middleware" AND exact phrase "rate limit"
5. Multiple Queries - queries=["authentication", "middleware"] - ANY of these terms

=== filament/core rules ===

## Filament
- Filament is used by this application, check how and where to follow existing application conventions.
- Filament is a Server-Driven UI (SDUI) framework for Laravel. It allows developers to define user interfaces in PHP using structured configuration objects. It is built on top of Livewire, Alpine.js, and Tailwind CSS.
- You can use the `search-docs` tool to get information from the official Filament documentation when needed. This is very useful for Artisan command arguments, specific code examples, testing functionality, relationship management, and ensuring you're following idiomatic practices.
- Utilize static `make()` methods for consistent component initialization.

### Artisan
- You must use the Filament specific Artisan commands to create new files or components for Filament. You can find these with the `list-artisan-commands` tool, or with `php artisan` and the `--help` option.
- Inspect the required options, always pass `--no-interaction`, and valid arguments for other options when applicable.

### Filament's Core Features
- Actions: Handle doing something within the application, often with a button or link. Actions encapsulate the UI, the interactive modal window, and the logic that should be executed when the modal window is submitted. They can be used anywhere in the UI and are commonly used to perform one-time actions like deleting a record, sending an email, or updating data in the database based on modal form input.
- Forms: Dynamic forms rendered within other features, such as resources, action modals, table filters, and more.
- Infolists: Read-only lists of data.
- Notifications: Flash notifications displayed to users within the application.
- Panels: The top-level container in Filament that can include all other features like pages, resources, forms, tables, notifications, actions, infolists, and widgets.
- Resources: Static classes that are used to build CRUD interfaces for Eloquent models. Typically live in `app/Filament/Resources`.
- Schemas: Represent components that define the structure and behavior of the UI, such as forms, tables, or lists.
- Tables: Interactive tables with filtering, sorting, pagination, and more.
- Widgets: Small component included within dashboards, often used for displaying data in charts, tables, or as a stat.

### Relationships
- Determine if you can use the `relationship()` method on form components when you need `options` for a select, checkbox, repeater, or when building a `Fieldset`:

<code-snippet name="Relationship example for Form Select" lang="php">
Forms\Components\Select::make('user_id')
    ->label('Author')
    ->relationship('author')
    ->required(),
</code-snippet>

=== .ai/migration rules ===

# Migration guideline: Old Laravel + tenancy DB → Filament v3 (prepare for v4)

This is a cleaned, lint-friendly version of the migration playbook. It contains the same guidance as the working draft but without duplicate headings or malformed lists.

## Goals / success criteria

- Produce a schema compatible with Filament v3 without data loss.
- Provide reversible, well-tested migrations and chunked backfills for central and tenant data.
- Minimize downtime and present a clear rollback strategy.
- Ensure tenant data is in tables with the `1_*` prefix and remove non-prefix tables only after verification.
- Rename tables to plural forms where required and update FK names to match the new naming scheme.

## Contract (inputs / outputs / error modes)

- Inputs:
  1. Repository migrations (`database/migrations/`).
  2. A cloned production DB (or staging copy) for schema comparison.
  3. The tenancy topology (single DB with tenant_id vs multi-DB per tenant).
- Outputs:
  1. Idempotent migration files (copy-and-swap) that do not conflict with existing migration ordering.
  2. Backfill jobs/commands that perform chunked, safe data copies.
  3. Optional `tenants:migrate` artisan scaffold for tenant-scoped execution.
- Error modes / failure cases:
  - Missing or unverified backups (mitigation: obtain and verify backups before proceeding).
  - Partially-applied migrations on the cloned DB (mitigation: inspect the `migrations` table before applying changes).

## Assumptions

- Work will be validated in staging first.
- Backups exist and are restorable.
- New migration filenames will be timestamped to sort after the newest repo migration.

## High-level plan

1. Inventory & backups
2. Map schema differences and design non-destructive migrations
3. Implement reversible migration files + backfill jobs
4. Add tenant-aware execution (runner or tenancy helper)
5. Update models, Filament resources and Livewire components
6. Write tests (Pest) and run verification
7. Staged rollout (staging → canary tenants → production)

---

## Inventory & backups

- Export schema and small data samples for each table (central and tenants).
- Identify tenancy pattern and package.
- Take and verify full backups for central and tenant DBs.

## Schema mapping & non-destructive prototyping

Use the copy-and-swap approach for renames and type changes:

1. Add new column/table (nullable)
2. Backfill data in chunks (queued job)
3. Deploy dual-write code (write to old and new)
4. Enforce NOT NULL and drop old column/table after verification

## Reversible migrations and backfills

- Write idempotent migrations with Schema::hasTable / Schema::hasColumn guards.
- Implement chunked backfills via `chunkById()` and queued jobs.

## Tenant-aware execution

- Prefer tenancy package helpers to run migrations across tenants when available.
- Otherwise implement `php artisan tenants:migrate` to iterate tenants and run tenant-scoped work.

## Code updates for Filament v3

- Update model `casts()`, add compatibility accessors/mutators, and update Filament resources and Livewire components.

## Tests & verification

- Write Pest tests for migration happy paths and Filament smoke tests.
- Run `vendor/bin/pint` and targeted tests before wider runs.

## Staged rollout & monitoring

- Use staging and tenant canaries, monitor checksums and representative rows.

## Rollback plan

- Keep old columns/tables until verification. Revert to old code if needed; remove old objects in a reversible migration.

## Practical tips & gotchas

- Chunk backfills and watch DB load.
- Rename FKs in separate migrations and update constraint names explicitly.

## Plan to detect and rename columns (concrete steps)

1. Inventory current state on the cloned DB

   - Run `php artisan migrate:status` to list applied migrations.
   - Export `information_schema.COLUMNS` for detailed column info.

2. Build expected schema from repo migrations

   - Parse `database/migrations/*.php` to extract schema operations (I can provide a scanner script).

3. Create a mapping file (old_name -> new_name)

   - Produce a JSON/YAML map of table/column/FK renames.

4. Generate safe migration stubs

   - Emit idempotent migrations (copy-and-swap) with timestamps newer than the latest repo migration.

5. Add backfill commands

   - Create artisan commands or queued jobs to backfill with safe chunk sizes.
